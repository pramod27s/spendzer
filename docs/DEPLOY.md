# Deploying Spendzer

Production layout: **API + Postgres on Render**, **frontend on Vercel**. The browser only ever talks to the Vercel domain. Vercel forwards `/api/*` to Render, so the refresh-token cookie stays first-party (`SameSite=Strict`) and no CORS is needed.

```
browser ──https──▶ spendzer.vercel.app ──/api/*──▶ spendzer-api.onrender.com ──▶ Postgres (Render)
                    (static React app)              (FastAPI, Docker)
```

## 1. Push the repo to GitHub

```bash
git add -A && git commit -m "Spendzer"
git remote add origin git@github.com:<you>/spendzer.git
git push -u origin main
```

`.env` is gitignored. Never commit real secrets or real statements.

## 2. API + database on Render

1. Render dashboard → **New → Blueprint** → pick the repo. It reads [`render.yaml`](../render.yaml) and creates:
   - `spendzer-db`: Postgres 16 (free plan)
   - `spendzer-api`: Docker web service from `backend/`, health check `/health`
2. Environment variables are set by the blueprint:
   | Variable | Value |
   | --- | --- |
   | `ENVIRONMENT` | `production`. The API refuses to start with a weak `JWT_SECRET` or `COOKIE_SECURE=false`. |
   | `DATABASE_URL` | from the database. `postgres://` URLs are converted to the async driver automatically. |
   | `JWT_SECRET` | generated by Render |
   | `COOKIE_SECURE` | `true` |
   | `CORS_ORIGINS` | `["https://<your-app>.vercel.app"]`. Only a fallback, since traffic is same-origin. |
   | `SEED_DEMO` | `true` re-creates the demo account on every deploy. Set `false` to turn the demo off. |
3. On each start the container runs [`backend/start.sh`](../backend/start.sh): migrations, then the category seed, then ML model training, then the demo (if enabled), then uvicorn on `$PORT`.
4. Note the service URL, e.g. `https://spendzer-api.onrender.com`. Check `https://…/health` returns `{"status":"ok"}`.

> The free plan sleeps after inactivity, so the first request after a while takes ~30 s.

## 3. Frontend on Vercel

1. Vercel → **Add New → Project** → import the repo → **Root Directory: `frontend`** (framework: Vite).
2. If your Render URL isn't `spendzer-api.onrender.com`, edit the rewrite in [`frontend/vercel.json`](../frontend/vercel.json):
   ```json
   { "source": "/api/:path*", "destination": "https://<your-api>.onrender.com/api/:path*" }
   ```
3. Deploy. No environment variables are needed. Optionally set `VITE_DEMO_EMAIL` / `VITE_DEMO_PASSWORD` if you change the demo credentials.
4. Put the Vercel URL into `CORS_ORIGINS` on Render.

## 4. Smoke test

- Open the Vercel URL → **Try the live demo** → the dashboard loads with the demo's months.
- Register a fresh account → onboarding → upload `backend/tests/fixtures/bank_split_columns.csv`.
- Reload the page: you stay signed in (refresh cookie works through the rewrite).

## Demo account

`demo@spendzer.app` / `spendzer-demo`: synthetic data, ~3 months plus the current one, built by [`app/seed/demo.py`](../backend/app/seed/demo.py). Visitors share it and can edit it, but can't delete it. It resets on every deploy, or by hand from the Render shell:

```bash
python -m app.seed.demo
```

## Retraining the category model

`python -m app.ml.train` (runs on every start). It learns from the seed keyword map plus every rule-, override- and user-categorized spend, as anonymized merchant text only.

## Alternative: Railway

Railway works the same way: a Postgres plugin plus a service from `backend/` (Dockerfile detected). Set the same variables; Railway provides `PORT` and `DATABASE_URL`. Point the Vercel rewrite at the Railway URL.
